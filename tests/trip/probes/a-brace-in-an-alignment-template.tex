% Braces in an alignment template, against braces in the entry itself.
%
% Measured against pdftex: they are not the same thing. What decides
% whether a tab or a \cr ends the entry is the braces the ENTRY has
% opened; the template's own do not count, even when one of them stays
% open across the whole entry.
%
%   \def\l#1{[#1]}
%   \halign{\l{#}\cr A\cr}      an ordinary alignment. The u part is
%                               `\l{' and the v part `}', so the macro's
%                               argument opens before the entry and closes
%                               after it, and the \cr between still ends
%                               the entry.
%   \halign{{#}\cr A\cr}        the same, with no macro in it.
%   \halign{#&#&\l{#}\cr ...}   three columns, the third of that shape --
%                               which is trip's own preamble on line 407.
%
% This engine counted the template's braces as the entry's, so the \cr was
% ignored, the entry ran on to the end of the file, and the run stopped.
% That is why trip's line 407 alignment took the whole rest of the file
% with it, and why the groups it left open swallowed the \let\PAR from
% line 404.
%
% NOT YET: braces the ENTRY itself leaves open. The reference puts in the
% } the column wants and reads the tab or \cr again --
%
%   ! Missing } inserted.
%   <inserted text>
%                   }
%   <to be read again>
%                      &
%   I've put in what seems to be necessary to fix
%   the current column of the current alignment.
%   Try to go on, since this might almost work.
%
% -- so `\halign{#&#\cr {A&B}\cr}' sets A and B in their own columns and
% the source's own } is left over, drawing "Missing \cr inserted" and
% then "Misplaced \cr" and then "Too many }'s". This engine ignores the
% tab and carries on; the boxes come out the same, only the diagnostics
% are missing.
%
% TRIED AND BACKED OUT: reporting it whenever the entry's brace count is
% not zero. The count cannot bear that weight yet, for two reasons found
% by measuring:
%
%   * A brace several scanners look at in turn is counted once per
%     reading. \hbox reads its `{' THREE times -- once for each thing the
%     token might have been -- so `\halign{#&#\cr \hbox{A}&B\cr}' thinks
%     the entry has two braces open when it has none.
%   * A nested alignment's braces are counted against the OUTER entry,
%     since the entry being tracked is still the outer one while the
%     inner preamble is read. That is what stopped gentle at its line
%     1074 and testmath at 114.
%
% WHERE THE THIRTY-ODD MISSING BRACES WENT. sample2e's one cell ended with
% the count at 35, and counting the braces by where they came from showed
% 36 opening braces and NOT ONE closing brace. Twenty-nine came from macro
% expansions.
%
% The reason: the scanner that absorbs a macro's argument takes a whole run
% of tokens from a list in one go rather than a token at a time -- that is
% where a macro call spends most of what it spends -- and it counts braces
% into its own depth as it goes. The entry never saw them. The opening
% brace of each argument WAS seen, because it is read singly before the run
% begins; its closing brace was swallowed with the rest. So every macro
% call with a braced argument left the entry one brace deeper.
%
% Telling the entry what that run consumed takes sample2e's cell from 35 to
% 2; skipping a re-reading takes it to 0. Suspending the outer entry for
% the whole of a nested alignment is the third piece.
%
% A FOURTH THING, found the same way: the count runs BELOW nought as
% readily as above it. A cell may close a brace it did not open -- the
% opening one having been swallowed by whatever put the cell's text
% together -- and holding the count at nought there loses the closing, so
% the next `{' leaves it looking one deep for good. That one clamp was
% costing amsmath's gather and multline a phantom brace per cell.
%
% Where it stands, counted as cells that would draw the fix-up if the
% report were turned on:
%
%   sample2e                    none
%   amsmath gather, multline    none
%   amsmath align, align*       still one per cell, 105 over testmath
%
% A FIFTH THING: skipping a re-reading is the wrong way round. A `{' that
% is put back and read again is skipped on the second reading, which is
% right when the first was counted -- but where the first reading never
% reached the entry at all, the brace is never counted and its `}' then
% takes the count below where it should be. The reference undoes a reading
% when it puts a token back instead, which keeps the pairing exact however
% many scanners look at the same brace, and that is what is done here now.
%
% NOT YET, and it is the whole of what is left: an align cell still ends
% holding one brace it never opened, 105 of them over testmath, where
% gather, multline and sample2e's tabular are all exactly right. The
% history of one such cell shows a `}' arriving with no `{' before it that
% the entry ever saw -- swallowed whole, somewhere the bulk accounting
% does not reach. Turning the report on stops testmath at line 317.
%
% Measured while looking: the reference does NOT suspend the count inside
% a box in a cell. `\halign{#\cr \hbox{A&B}\cr}' draws "Missing }
% inserted", then "Extra alignment tab has been changed to \cr", then
% "Missing \cr inserted" -- so the & inside the \hbox does end the entry,
% after the box is closed for it. This engine stops there instead.
\tracingonline=1\showboxbreadth=9999 \showboxdepth=9999
\font\tt=cmr10 \tt \def\l#1{[#1]}
\setbox0=\vbox{\halign{\l{#}\cr A\cr}}\showbox0
\setbox1=\vbox{\halign{\l{#}\cr A\cr B\cr}}\showbox1
\setbox2=\vbox{\halign{\l{#}&#\cr A&B\cr}}\showbox2
\setbox3=\vbox{\halign{#&\l{#}\cr A&B\cr}}\showbox3
\setbox4=\vbox{\halign{#&#&\l{#}\cr A&B&C\cr}}\showbox4
\setbox5=\vbox{\halign{{#}\cr A\cr}}\showbox5
\setbox6=\vbox{\halign{#{}\cr A\cr}}\showbox6
\end
